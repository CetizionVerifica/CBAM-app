### F1 — A password login reset the failure counter before the second factor (High, fixed)
- **Ref:** M1-R5, M1-R6
- **Found:** `auth.create_session` set `failed_count = 0` on every password success. Probe: five rounds of "right password, then 4 wrong codes". All 20 codes were checked, and the account ended with `failed_count: 4, locked_until: null`.
- **Fix:** `create_session` resets the counter only when sign-in is complete, which means a user without 2FA. `auth.clear_login_failures` runs after a successful code, a recovery code, or 2FA enrolment. It is internal; a test asserts `cbam_app` cannot execute it.
- **Retest:** Tests "F1: signing in again with the password does not reset second-factor failures" and "F1: a completed 2FA sign-in clears the failure count".

### F2 — Second-factor verification ignored the lockout (High, fixed)
- **Ref:** M1-R6
- **Found:** Probe: after session 1 locked the account (429), session 2 still got 400, 400, 400, so its codes were still being checked.
- **Fix:** When `record_login_failure` locks the account, it revokes every session that hasn't passed 2FA. `session_lookup` reports `locked`, and `/mfa/verify` refuses while locked. `mark_session_mfa_verified` and `use_recovery_code` also refuse while locked, in case a lock lands in between. Sessions that already passed 2FA carry on.
- **Retest:** Tests "F2: a lock stops guessing in every session still waiting for 2FA" and "F2: sessions that already passed 2FA are not ended by a lock".

### F3 — The RLS invitation policy allowed a staff account takeover from a consultant's context (High, fixed)
- **Ref:** G2, M1-R3, M1-R4
- **Found:** A consultant's request context inserted an invitation for an admin-invited platform admin (status `invited`, no open link), and accepting it returned 204.
- **Fix:** `invitation_access` WITH CHECK now requires the target user to be visible under `app_user` RLS and manageable by the caller: an admin, or a consultant for client-side users they created.
- **Retest:** Test "F3: the database refuses an invitation for a user the caller may not manage" (fails with a row-level security error).

### F4 — Client-supplied `X-Forwarded-For` decided the client IP (Medium, fixed)
- **Ref:** M1-R6, G10
- **Found:** With `trust proxy` hard-coded to 1 hop, `X-Forwarded-For: 203.0.113.77` was recorded as the client IP.
- **Fix:** New `TRUST_PROXY` setting (hop count or subnet list), default `false`.
- **Retest:** Test "F4: X-Forwarded-For is ignored unless a proxy is configured". **Deployment note:** set `TRUST_PROXY` to match the load balancer, or the rate limiter will key on the proxy's address.

### F5 — Assignment API and FKs not built yet (Medium, open)
- **Ref:** M1-R2, M1-R3, AT1
- The tables exist; the routes, the FKs to client and installation, and the `can_access_client` and `can_access_installation` helpers depend on M2's tables. This is by plan (Phase 1 order).
- **Closes with:** M2, including AT1 on real installation routes and re-verification of R2 and R3.

### F6 — A malformed `Referer` gave a 500 (Low, fixed)
- **Fix:** Safe parsing. A bad value counts as the wrong origin, giving 403 `bad_origin`. **Retest:** test "F6".

### F7 — A TOTP code could be reused within its window (Low, fixed)
- **Fix:** `auth.login_state.totp_last_step` records the last accepted step; a step at or before it is refused. **Retest:** test "F7: a TOTP code works only once".

### F8 — The 2FA set-up QR code might not match the stored secret (Not reproduced)
- **First pass (traced):** React StrictMode runs effects twice, so I expected two `/mfa/setup` calls to race.
- **Executed:** StrictMode does run effects twice under test (confirmed, `n: 2`), but with the once-per-mount guard removed, **only one** `/mfa/setup` call is made; React Query does not re-issue the mutation. The finding does not reproduce. The one-line guard is kept as harmless defence. The web test is kept as a behaviour check, not a regression test.

### F9 — A lockout during 2FA dropped the user on sign-in without explanation (Low, fixed)
- **Fix:** Sign-in shows "Too many failed attempts. Try again in 15 minutes." when it is reached because of a lock. **Retest:** web test "F9".

### F10 — Session and failure functions trust the user id the API passes (Info, accepted)
`auth.create_session` and `auth.record_login_failure` accept any `user_id`, so the password check lives in the API. Only `cbam_app` can call them. This is the intended trust boundary; anyone changing the auth routes should know about it.

### F11 — Email uniqueness across tenants reveals accounts (Info, accepted)
Inviting an address that exists in another tenant returns 409. It follows from D1's global email uniqueness, and only admins and consultants can see it.

## Spec gaps
These are for the spec owner to decide; the code does not assume answers.
1. **Forgotten password.** M1 has no reset flow. An admin can only deactivate and re-invite the user.
2. **Lost 2FA device and recovery codes.** No admin reset exists, so the user is locked out for good. Needed before go-live.
3. **Tenant management.** The spec says the platform admin manages tenants. M1 has only the CLI `bootstrap:admin`.
4. **Who may invite.** The spec is silent on consultants inviting. The implementation lets consultants invite contributors, reviewers and recipients (`INVITABLE_ROLES` in `packages/shared/src/access.ts`).
5. **Optional 2FA for other roles.** The API supports it, but there's no screen entry point yet.
