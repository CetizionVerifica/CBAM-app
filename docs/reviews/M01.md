## Findings

### F1 — A password login resets the failure counter before the second factor (High)
- **Ref:** M1-R5, M1-R6
- **Evidence:** In `…0002` line 345, `auth.create_session` sets `failed_count = 0` on every password success. Probe: five rounds of "sign in with the right password, then 4 wrong TOTP codes". **All 20 codes were checked, and the account ended with `failed_count: 4, locked_until: null`.**
- **Expected:** Anyone who knows the password gets at most 5 second-factor guesses before a lockout.
- **Actual:** Unlimited guesses at the 6-digit code, limited only by the per-IP rate limit, which F4 shows can be bypassed.
- **Fix:** `create_session` stops resetting the counter. Reset it only when 2FA verification succeeds, or at password login for users who have no 2FA.
- **Retest:** Test "password re-login does not reset second-factor failures".

### F2 — Second-factor verification ignores the lockout (High)
- **Ref:** M1-R6
- **Evidence:** `auth.router.ts` line 157, `/mfa/verify`, never reads `locked_until`. Probe: two unverified sessions. Session 1 made 5 wrong guesses and got 429 on the fifth. **Session 2 then got 400, 400, 400**, which means its codes were still being checked.
- **Expected:** Once the account is locked, every session of that user stops being able to try codes.
- **Actual:** Only the session that triggered the lock is revoked.
- **Fix:** Check the lock at the start of `/mfa/verify`. When the lock triggers, revoke all of the user's sessions that haven't passed 2FA (a new database function).
- **Retest:** Test "a lock stops guessing in every session".

### F3 — The RLS invitation policy lets a consultant's context take over an invited staff account (High)
- **Ref:** G2, M1-R3, M1-R4
- **Evidence:** `…0002` line 153. `invitation_access` WITH CHECK only requires the caller's role to be admin or consultant; it doesn't check the target user. Probe: an admin invites a platform admin, then deactivates and reactivates them (status `invited`, no open link). A consultant's request context then inserts an invitation for that user. **The insert succeeds, and accepting it returns 204**, setting the password of a platform admin account.
- **Expected:** The database refuses an invitation for a user the caller may not manage. The API already refuses this, because the consultant cannot see that user.
- **Actual:** Only the API check stops it. Any future route that inserts invitations without calling `loadUser` would allow privilege escalation.
- **Fix:** The WITH CHECK must require the target user to be visible to the caller and manageable by them: an admin, or a consultant with `created_by = self` and a client-side role.
- **Retest:** Repeat the probe as a test; the insert must fail with a row-level security error.

### F4 — Client-supplied `X-Forwarded-For` decides the client IP (Medium)
- **Ref:** M1-R6, G10
- **Evidence:** `app.ts` line 25 hard-codes `trust proxy` to 1 hop. Probe: a login with `X-Forwarded-For: 203.0.113.77` and no proxy in front. `auth_event.ip` recorded `203.0.113.77`.
- **Expected:** The proxy trust matches the deployment. A directly exposed API ignores the header.
- **Actual:** Wherever no proxy strips the header, a client can rotate the IP the rate limiter keys on and write false IPs into the audit trail.
- **Fix:** Add a `TRUST_PROXY` environment setting (hop count or subnet list), defaulting to off.
- **Retest:** Test that with the default config the recorded IP ignores the header.

### F5 — Assignment API and FKs are not built yet (Medium)
- **Ref:** M1-R2, M1-R3, AT1
- **Evidence:** `…0002` line 166. The tables exist, but there are no routes, no FKs, and none of the `can_access_client` or `can_access_installation` helpers.
- **Expected:** Admins and consultants can assign users to clients and installations, and contributors are limited to their installations.
- **Actual:** Deferred to M2, because the client and installation tables don't exist yet. This is by plan (Phase 1 order), not an oversight.
- **Fix:** Build it in M2, together with the FKs, the helpers, and AT1 on real installation routes.
- **Retest:** AT1 in the M2 test suite, and re-run this review's R2 and R3 rows.

### F6 — A malformed `Referer` gives a 500 (Low)
- **Ref:** Beyond spec
- **Evidence:** `platform/auth.ts` line 116, `new URL(referer)`, throws. Probe: a POST with `Referer: not a url` and no Origin returned 500.
- **Fix:** Parse it safely and treat a bad value as a wrong origin, which gives 403 `bad_origin`.
- **Retest:** Test for a malformed Referer.

### F7 — A TOTP code can be reused within its validity window (Low)
- **Ref:** Beyond spec (M1-R5)
- **Evidence:** `verifyTotp` accepts the current step ±1 and no used step is recorded.
- **Fix:** Store the last accepted time step per user and reject any step at or before it.
- **Retest:** The same code twice in a row: the second attempt is refused.

### F8 — The 2FA set-up screen can show a QR code that doesn't match the stored secret (Low)
- **Ref:** Beyond spec. Traced, not executed.
- **Evidence:** `TwoFactorSetupPage.tsx` line 30 starts set-up in `useEffect`. React StrictMode runs effects twice in development, so two `/mfa/setup` calls race, and the one that resolves last may not be the one that wrote the database last.
- **Fix:** Guard with a ref so set-up starts once per mount, or start it from a button.
- **Retest:** Web test that `/mfa/setup` is called exactly once.

### F9 — A lockout during 2FA drops the user on sign-in without explanation (Low)
- **Ref:** Design system 5.7 ("what happened, why, what to do")
- **Evidence:** `VerifyPage.tsx` line 31 navigates to `/sign-in` and the message is lost.
- **Fix:** Pass the reason to the sign-in screen and show it there.
- **Retest:** Web test.

### F10 — Session and failure functions trust the user id the API passes (Info)
- **Ref:** Design note
- `auth.create_session` and `auth.record_login_failure` accept any `user_id`, so the password check lives only in the API. This is acceptable because only `cbam_app` can call them, but it should be documented as a trust boundary.

### F11 — Email uniqueness across tenants reveals accounts (Info)
- **Ref:** Beyond spec
- Inviting an address that exists in another tenant returns "A user with this email address already exists." The cost is small (only admins and consultants can see it), and it follows from D1's global email uniqueness.

## Spec gaps
1. **Forgotten password.** M1 has no reset flow. At present an admin can only deactivate and re-invite the user.
2. **Lost 2FA device and recovery codes.** No admin reset exists, so the user is locked out for good.
3. **Tenant management.** The spec says the platform admin manages tenants. M1 has only the CLI `bootstrap:admin`.
4. **Who may invite.** The spec doesn't say whether consultants can invite users. The implementation lets consultants invite contributors, reviewers and recipients (the `INVITABLE_ROLES` setting).
5. **Optional 2FA for other roles.** The API supports it, but there's no screen entry point yet.
