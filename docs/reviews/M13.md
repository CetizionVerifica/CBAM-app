## Findings

### F1: A soft-deleted file on a draft period blocks every later version of that period (High)
- **Ref:** M3-R5, G4, M13-R4 (D15, "links to the period itself carry over")
- **Evidence:** Probe P1:
  1. Upload linked to v1 (draft), then `DELETE /evidence/:id` → 204.
  2. Submit, approve and issue v1 → 200.
  3. `POST /periods/:id/versions` → **500** `internal`.

  Cause: soft delete leaves the `evidence_link` rows in place. `copyPeriodEvidence` (`copiers.ts:10–20`) copies every link of v1, including links to deleted files. `app.evidence_resolve_target` (migration :111–114) then raises "This evidence has been deleted" (23503), which `errorHandler` does not map. The period can never get version 2.
- **Expected:** A new version is created; links to deleted evidence are skipped.
- **Actual:** 500 on every attempt, permanently for that period.
- **Fix:** In the copier, join `evidence_document` and keep only `deleted_at is null`. Also decide whether a soft delete should remove the file's links on draft versions in the same transaction (the audit keeps them). Add a test for this sequence.
- **Retest:** Repeat P1 and expect 201 with no link to the deleted file on v2.

### F2: The UI cannot link an existing file to a second record (High)
- **Ref:** M13-R1 ("one file can support many records"), design system 5.9, 6.11
- **Evidence:**
  - `apps/web/src/**` has no call to `POST /evidence/:id/links`. The only `/links` call is the unlink in `EvidencePanel.tsx:50`.
  - `EvidencePanel` offers upload only (`:111–126`).
  - Uploading the same file again is refused: "This file is already in the evidence library as “…”" (`evidence.router.ts:78`).
  - The library detail pane says "Link it from the record’s screen" (`EvidenceLibraryPage.tsx:240`), but that action does not exist.
- **Expected:** From a record's evidence panel (or the library detail pane), choose an existing file and link it.
- **Actual:** In the UI, a file can support only the record it was uploaded with, plus a copy on version n+1.
- **Fix:** Add "Link existing evidence" to `EvidencePanel`: a picker of the client's visible files, filtered by installation, that calls `POST /evidence/:id/links`. Make the duplicate-upload error offer "Link the existing file". Fix the text on line 240.
- **Retest:** A web test that links one file to an installation and to a period. Then check that the library shows two "Supports" chips.

### F3: Contributors can link and unlink files and links they did not create (Medium)
- **Ref:** G2, D15 ("contributors … edit or delete only their own uploads")
- **Evidence:** P2, as a contributor on installation A:
  - linking a consultant's file to a period → 201;
  - unlinking the consultant's link → 204;
  - unlinking another contributor's link → 204.

  `evidence_link_delete` (migration :322–324) checks only role and visibility. The API does not check who created the link (`evidence.router.ts:329–343`).
- **Expected:** A contributor removes only links they created, or links on files they uploaded. Whether a contributor may attach a consultant's file is a product decision: record it in D15.
- **Actual:** A plant user can remove the consultant's supporting evidence from a draft period. The audit trail records it.
- **Fix:** Add `and (app.can_manage_registry() or created_by = app.current_user_id())` to the link delete policy, and the same check in the route. State the link rule in D15.
- **Retest:** Repeat P2 and expect 403 for both unlinks.

### F4: Database link checks read the file under the caller's RLS, so a hidden or deleted file passes them (Medium)
- **Ref:** G1, G4, M13-R1 (D15, "the database resolves the link target")
- **Evidence:** In P9, running `withContext` as a contributor, direct INSERTs into `evidence_link` succeeded:
  - for a client-level file the contributor cannot see;
  - for a **soft-deleted file filed under installation B**, linked to installation A's period.

  Cause: `select installation_id, deleted_at into v_doc from evidence_document …` (migration :111) runs as the invoker. An invisible row yields NULLs, so the "deleted" and "another installation" checks are skipped. The API blocks this today only because `loadEvidence` runs first. Such rows would also trigger F1.

  Related: the dynamic `format('… public.%I …', new.record_table)` (:102) runs **before** the FK to `app.evidence_linkable` is checked, so the comment "checked … by the FK" is wrong. P9 with `record_table = 'app_user'` ran the query and failed on the client check, not the FK. No injection is possible (`%I`, schema fixed, RLS applies), but only the FK stops non-linkable tables.
- **Expected:** The trigger sees the document whatever the caller's RLS, and refuses non-linkable tables before running dynamic SQL.
- **Fix:** Read `evidence_document` through a small SECURITY DEFINER helper owned by `cbam_auth` (tenant-scoped, like `evidence_is_locked`). Refuse the insert when the caller cannot see the document. Check `exists (select 1 from app.evidence_linkable where table_name = new.record_table)` before the `execute`.
- **Retest:** Repeat P9 and expect both inserts refused.

### F5: The content check is weak for XLSX and file names without an extension (Medium)
- **Ref:** M13-R3
- **Evidence:** P4:
  - A 90-byte file (`PK\3\4` plus the text "[Content_Types].xml … xl/workbook.xml") uploaded as `.xlsx` → 201 as an XLSX. The test fixture `XLSX()` (`m13-evidence.test.ts:35`) is exactly such a non-workbook.
  - `fileName=pdf` (no dot) → 201; the key is stored without an extension, because `split('.').pop()` treats the whole name as the extension (`filecheck.ts:10`).
  - HTML text uploaded as `.csv` → 201. This is acceptable for CSV, but worth knowing.
  - A 25 MB+ upload gets the generic "This request is too large." (errors.ts:41), not the design system 5.9 wording. The web pre-check does show the right text.

  Any ZIP whose bytes mention those two names passes, including macro workbooks and archives of executables. No malware scan is configured.
- **Expected:** "At least content-type verification" that actually identifies an OOXML workbook.
- **Fix:** Parse the ZIP central directory (for example with `yauzl`, which works without extracting). Require the `[Content_Types].xml` and `xl/workbook.xml` entries, and refuse `vbaProject.bin` and macro content types. Require a real extension (`name.includes('.')`). Map the 413 on this route to the 5.9 message. Plan a scanner (ClamAV or Cloudinary add-on) before production and record it in D15.
- **Retest:** Repeat P4 and expect 400 for the fake XLSX and for `pdf`. Add a real minimal XLSX fixture.

### F6: An EU importer's user can give the operator's "client approval" (Medium)
- **Ref:** M13-R7, spec 4.10 ("approval by consultant and client"), spec §2 roles; Spec gap
- **Evidence:**
  - `verification.approveClient: ['contributor', 'recipient']` (`packages/shared/src/access.ts`).
  - Trigger :272–275.
  - Spec §2 defines the recipient as "Client management **or the EU importer**".

  A recipient approval was accepted in test :421, and the trigger does not distinguish operator staff from importer staff.
- **Expected:** Only operator-side users give the client approval.
- **Actual:** Any recipient assigned to the client can approve, including an importer's user.
- **Fix:** Decide who counts as the client, and record it in D15 and spec 4.10. Then restrict the approval, for example to contributors and to recipients flagged as operator staff, or add an explicit "can approve for client" assignment attribute.
- **Retest:** An importer-recipient approval → 403 in the API and 42501 in the DB.

### F7: The audit CSV export stops silently at 10,000 entries (Medium)
- **Ref:** M13-R5, design system 6.11 (export), 5.7 (errors state what happened)
- **Evidence:** `audit.router.ts:95–96` passes `limit: 10_000` with no signal in the file or headers. An admin's unfiltered export includes library imports and seeding, which alone produce thousands of rows.
- **Expected:** A complete export, or a clear refusal: "More than 10,000 changes match. Narrow the dates or client."
- **Actual:** A truncated file that looks complete to a verifier.
- **Fix:** Stream with the keyset cursor until done, or count first and return 422 with the rule. At minimum add a final "Export truncated at 10,000 entries" line and a header.
- **Retest:** Seed more than 10,000 rows; the export is either complete or refused with the message.

### F8: Existence oracles: the duplicate check and `evidence_is_locked` (Low)
- **Ref:** G1, G10
- **Evidence:**
  - P3: a contributor uploading a copy of a client-level file, or of an installation B file, gets 409 "This file is already in the evidence library." The partial unique index (:61) is client-wide, so they learn that the file exists (by hash) and cannot upload their own copy.
  - P13: a contributor calling `select app.evidence_is_locked('<invisible id>')` gets `true`, which reveals the lock state of a file they cannot see (a UUID is needed).
- **Fix:** Scope the uniqueness to what the uploader can see: `(client_id, coalesce(installation_id, …), sha256)`, or offer to link the visible copy. In `evidence_is_locked`, return false or null unless `app.evidence_visible(...)` holds for the document.
- **Retest:** Repeat P3 and P13.

### F9: The CSV export prefixes negative numbers with an apostrophe (Low)
- **Ref:** G6, D15 ("Numbers keep their exact digits")
- **Evidence:** P6 exports latitude `-33.868820` and longitude `-151.209290` as `'-33.868820` and `'-151.209290`. Cause: `csvCell` neutralises any leading `-` (`audit.router.ts:34`), and numbers arrive as strings.
- **Fix:** Skip neutralisation when the whole cell matches `^-?\d+(\.\d+)?([eE][+-]?\d+)?$`.
- **Retest:** Repeat P6; the cell reads `-33.868820`, and `=HYPERLINK(...)` is still neutralised.

### F10: A NUL byte in query or text input gives a 500 (Low)
- **Ref:** G8, Beyond spec
- **Evidence:** P5: `GET /audit?recordId=%00` → 500 `internal` (Postgres 22021). The same applies to any text field that goes to Postgres, for example evidence `title` and verification text.
- **Fix:** Reject `\u0000` in the shared `requiredText`, `optionalText` and `AuditQuery.recordId`, or map 22021 to 400 in `errorHandler`.
- **Retest:** Repeat the P5 request and expect 400.

### F11: CSV evidence must be UTF-8; Excel's default CSV export is refused (Low)
- **Ref:** M13-R3, design system 5.9 (accepts CSV)
- **Evidence:** P4: a Windows-1252 CSV containing "München" → 400 "This file is not a real CSV file…"; a UTF-16 CSV with BOM → 400. Excel's "CSV (Comma delimited)" writes in the system code page, so plant data with °, µ or accented names is refused with a misleading message.
- **Fix:** Accept any text without NUL or control bytes (allow high bytes), or give the message "Save the CSV as UTF-8 and upload again."
- **Retest:** Upload a CP1252 CSV → accepted, or refused with the UTF-8 message.

### F12: An empty verification record can be approved (Low)
- **Ref:** M13-R7, Spec gap
- **Evidence:** P11:
  - `PUT … { opinion: '' }` → 200 creates a row with every field null.
  - Consultant approval → 200; contributor client approval → 200.
  - The period's approve transition does not consult verification approvals (also 200).
- **Fix:** Require at least verifier name, accreditation and opinion before an approval, or show "Nothing to approve yet". Decide in the spec whether period approval or issue needs both verification approvals, or none (for example, unverified reports in the transitional period).
- **Retest:** Repeat P11; the approvals → 409 with the rule.

### F13: The evidence library does not have everything design system 6.11 and 5.8 ask for (Low)
- **Ref:** Design system 6.11, 5.8, 7
- **Evidence:** `EvidenceLibraryPage.tsx`:
  - filters are type and record type only; there is no **period** filter, although the API supports `periodVersionId` (`evidence.router.ts:221`);
  - there is no **preview pane**;
  - delete uses a confirm dialog without the 10 s Undo (5.8);
  - the list is capped at 500 rows (`evidence.router.ts:240`) with no paging or notice;
  - the autosave toast "Evidence saved" does not match the audit verb "Edit evidence" (13, "same verb").
- **Fix:** Add a period filter (the version select of the chosen installation) and an image/PDF preview through the signed link. Either adopt Undo or record the exception. Add paging or a "showing 500 of N" note. Align the verb.

### F14: The audit trail screen hides values for created and deleted records, and reviewers cannot filter by user (Low)
- **Ref:** M13-R5, M13-R6, design system 6.11
- **Evidence:**
  - `AuditTrailPage.tsx:173`: `changes = e.op === 'UPDATE' ? e.changes : []`. Inserts and deletes show "Created (n fields)" or "Deleted (n fields)", so an "Unlink evidence" entry does not show which record was unlinked.
  - The "Record" column shows the table name and a UUID, not a human label.
  - The user filter shows only with `users.list` (`:48`), so reviewers cannot filter by user in the UI, although the API allows it.
  - The record filter needs a pasted UUID, and no record screen links to its trail.
- **Fix:**
  - Let INSERT and DELETE rows expand to show their fields.
  - Resolve record labels as `recordLabels` does.
  - Build the user list from the actors present in the trail (`visible_user_ids()`).
  - Add a "View audit trail" link on record pages (`/audit?recordId=…`).

### F15: A contributor on the client page sees an upload zone that always fails (Low)
- **Ref:** Design system 5.7, G2 (UI consistency)
- **Evidence:** `ClientPage.tsx` mounts `<EvidencePanel recordType="client" …>` with no `installationId`, and `canUpload` is true for contributors (`EvidencePanel.tsx:38`). Every upload → 400 "Choose the installation this file belongs to." A client-level link would also be refused by RLS (P10: 403).
- **Fix:** For contributors, hide `EvidencePanel` on client-level records, or pass `canUpload = can(...) && (role !== 'contributor' || !!installationId)`.

### F16: A failed file clean-up is swallowed without a log (Low)
- **Ref:** Beyond spec (orphaned files)
- **Evidence:** `evidence.router.ts:210`: `files.delete(stored.key).catch(() => undefined)`. If Cloudinary delete fails, or the process dies between `put` and the insert, the file is orphaned and nothing records its key. P10 confirms the normal paths leave no orphans: in the duplicate race, 1 file stored and 1 refused; a refused link after upload leaves 0 extra files.
- **Fix:** Log the key at `warn` on failure. Optionally, run a periodic job that lists the Cloudinary folder and removes keys with no `evidence_document` row older than one day.

### F17: Intermittent failures in the API suite (Info)
- **Ref:** Beyond spec (test reliability)
- **Evidence:** 25 full runs of the API suite:
  - run 2: `m01-access > M1-R4 invitations > refuses a second user with the same email` failed;
  - run 7: `m03-periods.test.ts` failed at file level (its `beforeAll`), so 40 tests were skipped;
  - the other 23 runs passed.

  I did not see the M2 and M4 failures the builder reported, and I did not capture stack traces. Both failing setups sign users in with TOTP (`signInWithMfa` uses the current step, `nextCode` the next), so a 30 s step boundary during setup is a plausible cause. This is not confirmed.
- **Fix:** Run with `--reporter=verbose --retry=0` in a loop and keep the failing output. Check TOTP step handling in `helpers.ts`.

### F18: Storage keys appear in the audit trail (Info)
- **Ref:** G10
- **Evidence:** P14: 14 `evidence_document` audit rows carry `storage_key`, and consultants and reviewers can read them. The key alone does not open the file (`authenticated` delivery needs a signed link), so this is informational.
- **Fix (optional):** `register_business_table('public.evidence_document', '{storage_key}')`.

### F19: `evidence.read` is declared but not checked on the API routes (Info)
- **Ref:** G2
- **Evidence:** `access.ts` defines `evidence.read` (used only by the web nav and panel). The GET routes rely on RLS alone. A recipient gets `200 { evidence: [] }` (P15) where every other forbidden role/route pair in the app answers 403.
- **Fix:** Add `requirePermission('evidence.read')` to the three GET routes and the download route.

## Spec gaps

1. **Who is "the client" for the verification approval** (spec 4.10). The recipient role covers both operator management and importer staff (spec §2). See F6.
2. **Does period approval or issue need verification approvals?** The spec is silent, and today they are independent (F12). Because verification locks with the period, the verifier must record the opinion before the version is approved. Say so in the workflow (spec §7, step 7).
3. **Which evidence is "on" a period?** M13-R4 is implemented as "linked to the period or a record inside it". Files linked only to the installation, client or importer stay editable after issue. Confirm this in the spec.
4. **Retention of soft-deleted files and of the audit log.** D13 lists it as "check before production", but no requirement gives a period or a purge process.
5. **Malware scanning.** M13-R3 allows "at least content-type verification". D15 relies on that. A decision is needed before real client files arrive.
6. **CSV encoding** for evidence (F11) and for the audit export (UTF-8 with BOM today) should be written down.

2. **F2** (High): add "Link existing evidence" to the UI. This is needed before M5–M9 attach evidence to their records.

5. The Low findings can follow in the next UI pass. Re-review after steps 1 and 2 (re-run P1, P2, P9 and a web test for linking).
