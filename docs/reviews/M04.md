## Findings

### F1 — Publishing is not serialised with draft writes, so a published version can change, or differ from the diff that was reviewed (High, **fixed — verified at re-review**)
- **Ref:** M4-R2, M4-R4, G4 (Beyond spec: concurrency)
- **Evidence:**
  - `data.ts` 79–85: `loadDraft` reads `library_version` without a lock.
  - The trigger `guard_library_content` (migration 1128–1145) reads `status` with a plain `select`.
  - Publish (`library.router.ts` 153–167) is a plain `UPDATE … SET status = 'published'`. A factor write takes no lock on `library_version`, and publish takes no lock the writer respects. **Probe P1:** an edit that started before publish committed after it, and the published 2026.x now holds EF 77.
  - Publish also doesn't check that the draft still matches the diff shown in `PublishDialog`. A second admin (or a second tab) can edit or apply an import after the dialog loads, and the new content is published without being reviewed.
- **Expected:**
  - Once publish commits, the content is fixed.
  - What is published is exactly what the diff showed.
- **Actual:**
  - Content can be committed into a published version.
  - Publish doesn't know which diff was reviewed.
  - The window for the P1 race is narrow (the writer's last statement). The stale-diff case needs only two admins, or two tabs.
- **Fix:**
  1. Every write path locks the version row: `loadDraft(tx, id, { forUpdate: true })` → `select … for update`. This covers factor add, PATCH and DELETE, goods-category PATCH, precursors PUT, import preview, import apply, draft delete and publish.
  2. In `guard_library_content`, read the parent with `for share`, so direct DB writers are serialised against publish too.
  3. `GET /diff` returns a fingerprint of the draft content (reuse `datasetState`'s hash over all datasets). `POST /publish` takes `{ confirmCode, diffFingerprint }` and answers 409 `stale_diff` when the fingerprint no longer matches.
- **Retest:**
  - Probe P1 as a test (two transactions, the writer holds, then publish). Expect the publish to wait and then either commit after the write or refuse the write.
  - A test that edits a factor between `GET /diff` and `POST /publish`. Expect 409.
- **Re-review (verified):**
  - `loadDraft` takes `select … for update` (`data.ts` 84). It is called before any content write on every write route:
    - factor POST, PATCH and DELETE (`library.router.ts` 246, 262, 281)
    - goods-category PATCH and precursors PUT (through `loadCategory`, 292)
    - import upload (401)
    - import apply (435, before the fingerprint check)
    - discard (154)
    - publish (174)
  - The only write that doesn't take the lock is draft creation (131–149). It writes only the new, uncommitted version, and `library_version_one_draft` covers it.
  - `guard_library_content` reads the parent `for share` (migration 1184). Publish recomputes the diff under the lock and compares its SHA-256 with the reviewed fingerprint (181).
  - `diffRecords` sorts by key, and `loadFactors`, `loadCnCodes` and `loadGoods` all `order by`, so the fingerprint is deterministic. Q5 shows it matching after a successful publish.
  - The regression test "an edit that started before publish…" would fail without the lock: publish would read the uncommitted old content, match the fingerprint and commit.
  - Q1 covers the reverse order. Q5 shows no deadlock under mixed concurrent writes.
  - The residual notes are F17 and F20.

### F2 — The admin of any tenant can change the platform-wide library, and the change is logged only in that tenant (High, **fixed — verified at re-review**)
- **Ref:** M4-R5, G1, G3, D1 (also a Spec gap)
- **Evidence:**
  - `auth.bootstrap_tenant` (M1 migration 577–597) makes the first user of **every** tenant a `platform_admin`.
  - M4 grants library writes to that role with no tenant condition: `access.ts` 38, and `app.is_platform_admin()` (migration 77–79) is used by the policies at lines 1254–1265.
  - The M4 tests show it themselves: each test file's `adminOfNewTenant()` creates a new tenant, and its admin publishes the shared library.
  - The audit row takes the actor's tenant (migration 57–59), and `audit_log_read` shows each tenant only its own rows (M1 migration 643–644). Tenant A's admin can't see that tenant B's admin changed the EF that A's next period will pin.
- **Expected:** Only the platform operator (CETIZION, spec §2) publishes the library that every tenant pins. Every tenant can trace library changes.
- **Actual:**
  - Any tenant admin can create, import and publish.
  - The history is visible only to the tenant that made the change.
- **Fix:**
  - Mark the operator tenant, for example `tenant.is_platform boolean` (set only through the bootstrap CLI).
  - Make `app.is_platform_admin()` require `role = 'platform_admin' and tenant is_platform`, and keep `library.write` in the API behind the same check.
  - Log library changes with a null `tenant_id` (or the platform tenant's id) and let every tenant's admin read `public.library_*` and `template_version` rows.
  - Record the role split in the spec: a platform admin versus a tenant admin.
- **Retest:** A second tenant's `platform_admin` gets 403 on `POST /library/versions` and publish, and RLS refuses a direct DB insert. The first tenant's admin sees the library audit rows.
- **Re-review (verified):**
  - `tenant.is_platform_operator` has a unique partial index (migration 87–88).
  - `app.is_library_admin()` (90–95) is in the insert, update and delete policies of all 8 library tables, including `template_version`, and in `library_import` (1304–1318).
  - `cbam_app` has only SELECT on `tenant` (M1 migration 63), so the app role can't make its own tenant the operator (test, 42501).
  - `auth.set_platform_operator` is SECURITY DEFINER, owned by `cbam_auth`, revoked from public and granted only to `cbam_owner`. It is audited (Q9).
  - The API `requireOperator` is on all 9 write routes. Q2 found no path for another tenant's admin, through the API or the DB.
  - Override approval still uses the tenant-scoped `app.is_platform_admin()` (migration 1245 and 1330). That is consistent with overrides being tenant data, but D11 and D12 don't say it (F19).
  - The audit half of the fix was settled by D12 (entries stay in the operator's trail), not by making them visible to every tenant (F19).

### F3 — Default values for electricity can't be stored in their unit (Medium, **partly fixed — still open**)
- **Ref:** M4-R1, G5
- **Evidence:**
  - `library.ts` 30: `default_see: ['see']`, which allows only `tCO2e/t` and `kgCO2e/t`.
  - The seed has the goods category `electricity` with unit `MWh` (migration line 384) and CN `27160000` (line 1060).
  - **Probe P3:** `tCO2/MWh` is refused with 400.
- **Expected:** A default value is per unit of the good: tCO₂e/t for goods measured in tonnes, tCO₂e/MWh for electricity.
- **Actual:** Electricity default values are refused. An admin could enter them as tCO₂e/t to get past validation, which labels the value wrongly.
- **Fix:**
  - Add a `see_electricity` dimension (`tCO2e/MWh`) to `units.ts`.
  - Allow it for `default_see` only when the CN code's goods category has `unit = 'MWh'`. Check this in the router, which knows the version. In the Zod rule, allow either dimension.
  - Update `docs/mappings/library-import.md`.
- **Retest:** 27160000 in `tCO2e/MWh` → 201. 72081000 in `tCO2e/MWh` → 400.
- **Re-review (still open, Medium):**
  - The `see_electricity` dimension was added, and `default_see` allows it (`packages/shared/src/library.ts` 30, `units.ts`).
  - But the second half of the fix was not done: nothing ties the unit to the goods category of the CN code.
  - **Q3:** steel 72081000 in `tCO2e/MWh` → 201, electricity 27160000 in `tCO2e/t` → 201, and a CSV row for steel in `tCO2e/MWh` → 201.
  - `value_si` is 0.5 in both `tCO2e/t` and `tCO2e/MWh`. So a default value with the wrong dimension reaches the engine as a number in the wrong unit per good, and the SEE is wrong unless M10 checks the dimension.
  - The retest "72081000 in `tCO2e/MWh` → 400" fails.
  - `docs/mappings/library-import.md` was not updated.
  - **Fix:** in the factor POST/PATCH and the import `checkReferences` (`library.router.ts` 242–275 and 365–385), look up the CN code's goods category in the draft. Require `see_electricity` exactly when its unit is `MWh`, and `see` otherwise.

### F4 — Plausible range bands are optional, missing from the seed and overrides, and not normalised (Medium)
- **Ref:** M4-R8, G5
- **Evidence:**
  - `library.ts` 107–108: `plausibleMin`/`Max` are optional.
  - Migration lines 234–235 allow null.
  - The seeded GWPs and natural gas EF have no bands (lines 1064–1073).
  - `OverrideFields` (`library.ts` 242–246) has no bands, and an override value isn't checked against the library band.
  - Bands are stored "in the same unit as the value" (line 218) with no SI copy. If a PATCH changes `unit`, the bands silently change meaning.
- **Expected:** Each factor has bands that M11 can use.
- **Actual:**
  - A factor can be published without bands.
  - M11 would have to convert the bands itself.
  - Overrides, which most need a plausibility check, have none.
- **Fix:**
  - Store `plausible_min_si`/`plausible_max_si` next to the entered bands, computed in `withSi`.
  - List the factors without bands in the publish dialog as a warning, or require bands for `ncv`/`emission_factor`/`grid_factor` (decide in the spec).
  - Warn when an override value falls outside the library band for the same key.
  - Add bands to the seeded natural gas EF (for example, from IPCC ranges) or record why it has none.
- **Retest:** A factor in `MJ/kg` with bands has SI bands equal to its bands in `TJ/t`. The publish preview lists the factors without bands.

  - The test "F5: two previews applied at once" passes.
  - Q6 applied the same preview twice: 200 and 409.
  - Q5 applied an import alongside factor adds: 409 `stale_preview`.

### F6 — Overrides aren't pinned, and the approval flow has gaps (Medium)
- **Ref:** M4-R3, M4-R5, D11 (also a Spec gap)
- **Evidence:**
  - `client_factor_override` (migration 288–323) has no `library_version_id` or period link. Approving or withdrawing one changes what the next calculation of **any** period of that client uses, including a period that already pinned its library version.
  - `overridesRouter` 187–191 and migration 1193–1194 and 1281–1284 let the proposer withdraw an **approved** override on their own. Probe P7: the admin approves, then the consultant withdraws, and both get 200.
  - The admin can approve their own proposal (probe P7: 200). No second person checks it.
- **Expected:** Nothing an admin approved changes silently for a period that has already pinned its inputs, and changes to approved values are checked by a second person.
- **Actual:** Override state is live and global to the client.
- **Fix:**
  - Decide in the spec (with M3 and M10) that a period version snapshots the ids of the overrides it uses, the same way it pins the library version.
  - Allow only the platform admin to withdraw an approved override. The proposer may withdraw only while it is `proposed`.
  - Block `decided_by = created_by` in `guard_factor_override`, or record self-approval as an explicit exception with a reason.
- **Retest:** A consultant gets 403 on withdrawing an approved override. An admin gets 409 or 403 on approving their own proposal.

### F7 — Two admins creating a draft at the same time get a 500 (Low, **fixed — verified at re-review**)
- **Ref:** Beyond spec
- **Evidence:** `library.router.ts` 118–126 checks for a draft and then inserts. The losers hit the unique index `library_version_one_draft` (migration 118), which is not in `VERSION_UNIQUE` (line 50). **Probe P2:** `201, 500, 500`.
- **Fix:** Map `library_version_one_draft` to 409 `draft_exists`, or take the F1 lock first.
- **Retest:** Parallel creates return one 201 and 409s.
- **Re-review (verified):** `VERSION_UNIQUE` maps `library_version_one_draft` (`library.router.ts` 52–56). The test "F7: two drafts created at once" gives 201 and 409.

### F8 — The 10 MB body parser runs before authentication, and the "too large" message is wrong for most routes (Low, **fixed — verified at re-review**)
- **Ref:** G10
- **Evidence:**
  - `app.ts` 30–33 chooses `jsonImport` (10 MB) by path, before `requireAuth`. **Probe P6:** an anonymous 9 MB body is parsed in full, then answered 401.
  - `errors.ts` 42 says "Files can be at most 8 MB" for every 413, including the 1 MB routes. The limits are also inconsistent: 8 M characters, but 10 MB for the body.
- **Fix:**
  - Mount the large parser after `authenticate` and require a session (and the `library.write` permission) before parsing.
  - Word the 413 message per route, or keep it generic ("This request is too large.").
- **Retest:** An anonymous 9 MB POST is refused before parsing (401 or 413 fast). A 2 MB body on `/clients` shows a generic message.
- **Re-review (verified):**
  - `app.ts` 31–33 skips the global parser for the import path only.
  - The route runs `requirePermission`, then `requireOperator`, then `express.json({ limit: '10mb' })` (`library.router.ts` 394).
  - `requireAuth` runs before all of them (69), and `requireSameOrigin` and `authenticate` don't read the body.
  - Q4: requests are refused before parsing (anonymous: the socket closes in under 60 ms; consultant and non-operator admin: 403 in about 50 ms). The 413 message is generic.
  - Express 5 forwards the rejected promise if the `requireOperator` DB lookup fails, so there is no unhandled rejection.

### F9 — The factor tables and import preview don't scale to a real default-value file (Low)

### F10 — Factor subjects are free text, so keys are fragile, and an override can target nothing (Low)

### F17 — Draft lock notes for M3: `for update` blocks FK inserts, and the trigger's `for share` depends on RLS (Info, new at re-review)
- **Ref:** G4, M4-R3 (Beyond spec: concurrency)
- **Evidence:**
  - `loadDraft` uses `forUpdate()` (`data.ts` 84). FOR UPDATE conflicts with the FOR KEY SHARE that every FK insert referencing `library_version` takes. Once M3 pins library versions from `period_version`, a period pin on that version will wait for any draft write or publish holding that row. Today the longest is a 20,000-row apply of about 2.4 s (Q7).
  - `guard_library_content` reads the parent `for share` (migration 1184). For a locking read, Postgres also applies the UPDATE policy, and for `library_version` that is `app.is_library_admin()`. So for any role that is not a library admin, the parent is hidden and `v_status` is null. The trigger treats that as a cascade delete and allows the write.
  - This is safe today only because every content table has the same `is_library_admin()` write policy. The migration comment at 1170 says so.
- **Suggestion:**
  - Use `forNoKeyUpdate()` in `loadDraft`. It still conflicts with FOR SHARE, so the serialisation holds, but it doesn't block FK inserts.
  - In the trigger, tell "parent deleted in this transaction" apart from "parent not visible", or make the status lookup SECURITY DEFINER, so the guard doesn't rest on the policies staying aligned.

### F18 — Import apply is about 60 % slower after the fixes (Info, new at re-review)
- **Ref:** Beyond spec (performance); design system §12
- **Evidence:** Q7: a 20,000-row apply takes 2,449 ms, against 1,514 ms in P4. Each inserted row now evaluates `app.is_library_admin()`, which queries `tenant`, in the insert policy, and takes a row-level `for share` on the same version row in `guard_library_content`.
- **Suggestion:** Write the policies as `with check ((select app.is_library_admin()))`, so the planner evaluates it once per statement (an initPlan). Consider a statement-level status check for bulk inserts. This is not blocking. Track it with F9.

### F19 — F2 residuals: library audit visibility and override approval by tenant admins aren't in the spec (Info → Spec gap, new at re-review)
- **Ref:** G3, M4-R5, D11, D12
- **Evidence:**
  - Q9b: all library audit rows carry the operator tenant's id. D12 accepts this. But a verifier working through a non-operator tenant can't see who changed the EF its period pinned, which was the second half of F2.
  - Override approve and reject still check the tenant-scoped `app.is_platform_admin()` (migration 1245 and 1330; `access.ts` 42 `overrides.decide`). So each tenant's own admin approves its clients' overrides, not the operator. That is consistent with RLS, since the operator can't see other tenants' clients, but D11 and D12 don't state it.
  - With no operator set, the library is read-only for everyone, and the UI gives no hint why (`LibraryPage.tsx` 56).
- **Suggestion:**
  - Record in D12 whether tenants may read the library's audit history, for example through a read-only library-history view.
  - Record who approves overrides: the tenant admin or the operator.

### F20 — The publish fingerprint covers only the fields shown in the diff (Info, new at re-review)
- **Ref:** M4-R2, M4-R4
- **Evidence:**
  - `factorRecord` (`data.ts` 165–178) compares `value`, `unit`, validity, bands, `source` and `notes`. It doesn't compare `value_si` or `si_unit`.
  - The goods-category records leave out `template_name` and `sort_order`.
  - Through the API, `value_si` is always derived with `withSi`. But a direct DB write by the operator that changes only `value_si` would publish without changing the fingerprint. That is the value the engine will use.
- **Suggestion:** Include `valueSi`/`siUnit` in the fingerprint input, even if the diff view hides them. Alternatively, add a DB CHECK or trigger that recomputes `value_si` from `value` and `unit`.

## Spec gaps

7. **Library audit visibility and override approver under D12 (F19).** Can non-operator tenants read the library change history? Does the tenant admin or the operator approve client overrides?
