## Findings

### F1 — Status history rows can be forged by any role that sees the installation (Medium)
- **Ref:** G2, M3-R3, Beyond spec
- **Evidence:** In `20260929000005_m03_periods.sql:368-372`, policy `period_status_change_insert` and `grant select, insert on period_status_change to cbam_app` allow inserts by every visible role. Probe P3: a contributor inserted `from_status 'in_review', to_status 'approved', reason 'forged'` as `cbam_app` → **inserted**. Probe P5: the reviewer's `GET /periods/:id` then showed `["approved", "Kiran"]` in the history, with the contributor shown as the approver.
- **Expected:** Only the status trigger writes history. The history is evidence of sign-off.
- **Actual:** No API route writes it, but RLS, the second line of defence, does not stop a direct write. The audit log does record the real inserter.
- **Fix:**
  - Drop the insert policy and the INSERT grant for `cbam_app`.
  - Make `app.log_period_status()` SECURITY DEFINER, owned by `cbam_auth` with a fixed `search_path`, and grant it INSERT on `period_status_change`.
  - Optionally add a check that `to_status` equals the version's current status at insert time.
- **Retest:** a direct insert as a contributor, consultant or admin fails with 42501, and status changes through the API still write history.

### F2 — No range on period dates; years below 100 give a wrong end date and a 500 (Medium)
- **Ref:** M3-R2, G8, Beyond spec
- **Evidence:**
  - `periodEndDate` in `packages/shared/src/periods.ts` uses `Date.UTC(y + 1, …)`, which maps years 0–99 to 1900–1999. `periodEndDate('0050-01-01')` returns `1950-12-31`.
  - `'9999-06-01'` gives `'+010000-05-31'`.
  - Probe P1: `POST /installations/:id/periods {startDate: '0050-01-01', endDate: '1950-12-31'}` passes Zod, then fails the DB check → **500 `internal`**.
  - Probe P1b: a 1950 calendar year is accepted with 201.
- **Expected:** Periods stay within a plausible CBAM range. Invalid input gets a 400 with a field message.
- **Actual:** Any year from 0001 to 9999 passes `IsoDate`.
- **Fix:**
  - In `PeriodInput`, refuse starts before 2023-01-01 (CBAM began Oct 2023) or after 2100-12-31, with a message like "Choose a start date between 2023 and 2100."
  - Mirror this with a DB check on `start_date`.
  - Build the date with `setUTCFullYear` so the helper is correct for any year.
- **Retest:** the P1 and P1b probes → 400. Unit tests for `0050-01-01` and the range bounds.

### F3 — Portfolio shows no period or status (Low)
- **Ref:** Design system 6.1 ("Portfolio — M1, M2, M3"), §13 "Context bar shows … period and status"
- **Evidence:** `PortfolioPage.tsx:11` still says period and status columns "join as M3 … provide them". Probe P10: `GET /clients` returns only `id, legalName, countryCode, city, installationCount`.
- **Expected:** The portfolio shows each client's current period and status, including the "periods in review" count under "Needs attention".
- **Actual:** Periods can only be reached through client → installation.
- **Fix:** Add the latest period and status per client or installation to `GET /clients` (one aggregate query), and add the Period and Status columns and the in-review count.
- **Retest:** web test for the columns, and API test that the aggregate respects RLS.

### F4 — `based_on_version_id` is not checked to be the previous version (Low)
- **Ref:** M3-R5, Beyond spec
- **Evidence:** Probe P4: a direct insert of version 2 of period A with `based_on_version_id` pointing at period B's version 1 → **inserted**. The API always sets it correctly.
- **Fix:** In `guard_period_version` on INSERT, require `based_on_version_id` to be the id of `version_no - 1` of the same period when `version_no > 1`.
- **Retest:** the probe → 23514.

### F5 — History hides the actor when the viewer cannot see that user (Low)
- **Ref:** M3-R3, Beyond spec
- **Evidence:** Probe P5: an admin's "Submit for review" shows `changedBy: null` to the reviewer. The UI shows "A user you cannot see", because `app_user` RLS hides unassigned users (`periods.router.ts`, `periodDetail`).
- **Expected:** A verifier can see who submitted, approved and issued.
- **Fix:** Store the actor's display name on `period_status_change` at write time (trigger, from `app_user` via the definer function in F1), or expose names through a narrow SECURITY DEFINER lookup limited to actors in the period's history.
- **Retest:** a reviewer sees the admin's name in the history.

### F6 — The approved-lock banner tells every role to "return it to draft" (Low)
- **Ref:** Design system 5.7 and 9 (state the rule, plain words), M3-R3
- **Evidence:** `PeriodPage.tsx:97-103` shows the same text to reviewers, contributors and admins, who cannot return a period to draft.
- **Fix:** Consultants keep "Return it to draft to make changes." Everyone else sees "This period is approved and read-only. A consultant can return it to draft."
- **Retest:** web test per role.

### F7 — Shell pieces for periods not yet built (Low)
- **Ref:** Design system §4 and §6.3
- **Evidence:**
  - `ContextBar.tsx`: crumbs are plain text, not switchers, even though M3 now provides the period lists.
  - There are no "This period" workflow steps in the side nav.
  - The period overview has no Team panel. The M2 team API exists.
  - The progress bars depend on M5+.
- **Fix:** Make the period crumb a switcher using `GET /installations/:id/periods` and add the Team panel now. The side-nav steps and progress bars can arrive with M5.
- **Retest:** web test for switching periods from the context bar.

### F8 — The approval guard is enforced in the API only (Info)
- **Ref:** M3-R7, G4
- **Evidence:** Probe P9: a reviewer's direct `update period_version set status = 'approved'` succeeds. Nothing in the database knows about blockers yet.
- **Note:** This is acceptable until M11 exists (D6). When M11 adds findings, also enforce "no open critical findings" in `guard_period_version` on the in_review → approved step.

### F9 — Recipients see draft periods (Info, spec gap)
- **Evidence:** Probe P2: a recipient assigned to the client gets 200 on a draft period.
- **Note:** The spec says recipients "view and download approved outputs". Decide whether recipients see periods before approval. If not, add `status in ('approved', 'issued')` or `version_no > 1` visibility for the recipient role in the read policies.

### F10 — `app.assert_period_writable` reveals whether a version id exists (Info)
- **Evidence:** Probe P8: an unknown id → 23503, while an existing locked one → 55000 and an existing unlocked one → ok, whoever the caller is.
- **Note:** Ids are random UUIDs and the function is reached only through triggers and API code, so the practical risk is negligible. Say so in the function comment, or return the same error for "unknown" and "not visible".

### F11 — Admin cannot return a period to draft (Info, spec gap)
- **Evidence:** D14 reads M3-R3 literally. The API returns 403 "Only a consultant can return a period to draft." and the DB returns 42501.
- **Note:** Confirm with the product owner. If admins should, change `PERIOD_TRANSITIONS.reopen.roles` and the trigger.

### F12 — Spec gaps around versions and issue (Info)
- A draft version cannot change its library pin (no endpoint). The spec does not say whether a draft may move to a newer library version.
- Issue is allowed without generated outputs. Spec workflow step 9 ties issue to shared outputs. When M12 lands, gate `approved → issued` on a generated report version.

## Spec gaps
1. Plausible date range for reporting periods (F2).
2. Whether the admin may return a period to draft (F11).
3. Recipient visibility of unapproved periods (F9).
4. Whether a draft version may re-pin to a newer library version (F12).
5. Whether issue requires a generated report version (F12).
