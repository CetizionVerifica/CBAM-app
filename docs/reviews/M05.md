## Findings

### F1 — Production balance check is switched off by any internal-use row with no amount (High)
- **Ref:** M5-R3, AT2, D20
- **Evidence:** `packages/shared/src/processes.ts:306` makes `allEntered` require every internal use to have an amount, otherwise `difference = null` and `withinTolerance = null`. M5-C05 fires only on `=== false` (:353). The missing amount is only M5-C06 **warning** (:347-351). `canComplete` looks only at critical checks. Probe P1: AL 1,000 t, good 1,200 t, internal use to "Rolling mill" with `amount: null` → balance `{"difference":null,"withinTolerance":null}`, checks `[["M5-C06","warning"]]`, `POST /complete` → **200 complete**. `copyProcessSetup` (`copiers.ts:110-117`) creates exactly these null-amount rows on every clone.
- **Expected:** A process whose goods exceed its activity level (AT2) can never be marked complete. An incomplete balance must block completion.
- **Actual:** An empty internal-use row hides any imbalance, and the UI then shows "All checks pass. The process can be marked complete."
- **Fix:** Make M5-C06 critical, or compute the balance with the missing amounts treated as unknown and raise a critical "balance cannot be checked" when `allEntered` is false while routes are complete. Alternatively, evaluate `al − goods − known uses − nonCbam < −tolerance`, which already proves an over-allocation.
- **Retest:** Probe P1 (1,200 vs 1,000 with an empty internal use) → `POST /complete` returns 409 `checks_open`.

### F2 — Deleting a consuming process changes a complete supplier's balance without returning it to draft (Medium)
- **Ref:** D20 ("any change to a process or its data returns it to draft"), M5-R3
- **Evidence:** `process_internal_use.consumer_process_id … on delete cascade` (migration :423-424); `DELETE /processes/:id` (`processes.router.ts:342-362`) lists `consumedHere` but never calls `backToDraft` for the supplier. Probe P2: Potline complete and balanced (1,000 = 700 + 300 to Rolling mill). After deleting Rolling mill with confirmation, Potline is `complete` with `[["M5-C05","critical"]]`.
- **Expected:** The supplier returns to draft, because its data changed and a critical check is open.
- **Actual:** It stays complete with a critical check open.
- **Fix:** In the delete handler, set every process in `consumedHere` back to draft, using the same `backToDraft`. Consider a DB trigger on `process_internal_use` delete/update that sets its producer back to draft.
- **Retest:** Probe P2; expect the supplier `status: 'draft'`.

### F3 — Ten-category limit (template G1–G10) can be exceeded by concurrent requests (Medium)
- **Ref:** D16, G8
- **Evidence:** `checkCategoryCount` (`processes.router.ts:115-125`) reads the whole version, but only `POST` locks the period version (`:221`, `forNoKeyUpdate`). `PATCH /processes/:id` locks only its own process row (`:260`). There is no DB constraint. Probe P12: sequentially, PATCH adding an included category and then POST a new category gives 200/409 and 10 categories. Run concurrently (`Promise.all`), the result was 200/201 and **11 distinct categories in 4 of 4 attempts**.
- **Expected:** At most 10 distinct categories per period version, always.
- **Actual:** 11 can be saved. M12 has only 10 rows in `A_InstData` (a), so the export will fail or truncate.
- **Fix:** Lock the period version row (`FOR NO KEY UPDATE`) in PATCH before `checkCategoryCount`, as POST does. Also consider a deferred constraint trigger that counts categories per version.
- **Retest:** Probe P12 → one of the two concurrent requests answers 409 `too_many_categories`.

### F4 — Qualifying parameter numbers are not range-checked; a negative value returns 500 (Medium)
- **Ref:** M5-R4, G8
- **Evidence:** `ParameterValueInput` (`processes.ts:111-117`) uses `quantityInput(QUALIFYING_DIMENSIONS)` with no bounds; the API (`processes.router.ts:556-572`) checks only the dimension. The DB CHECK `app.amount_ok` (migration :148-152, :391-392) rejects negatives with 23514, which `mapDbError` and `errors.ts` do not map. Probe P3: `-5 %` → **500** `internal`; `150 %` → **200**, stored `si: 1.5`; `999999 t/t` → 200.
- **Expected:** 400 with a field message. Fractions (% Mn, clinker factor, % N) are limited to 0–100 %. Mass ratios are ≥ 0, with a plausibility band.
- **Actual:** Server error for negatives; impossible percentages are accepted and would be written to `Summary_Products`.
- **Fix:** Refine in `ParameterValueInput`: value ≥ 0, and for `fraction` si ≤ 1. Mirror this in the DB (a CHECK on `value_si` by dimension, or in `guard_process_good_parameter`).
- **Retest:** Probe P3 → 400 for both, with `path: ['parameters', 0, 'quantity', 'value']`.

### F5 — Data source longer than 500 characters returns 500 (Medium)
- **Ref:** G8, G5/G7
- **Evidence:** `quantityInput` source is `z.string().trim().min(1)` with no max (`packages/shared/src/quantity.ts:22`). The DB requires `length between 1 and 500` (migration :141). Probe P11: a 600-character source on a route amount → **500**.
- **Expected:** 400 "Use at most 500 characters." on the source field, in the shared schema (the form shows it too).
- **Actual:** 500.
- **Fix:** Add `.max(500, …)` in `quantityInput`. It is shared, so other modules benefit.
- **Retest:** Probe P11 → 400 with `path: [..., 'source']`.

### F6 — Category or route change does not consult later modules' dependents (Medium)
- **Ref:** M5-R5, D22 ("Later modules (M6–M9) add their own dependent records through `processDependents` so the list stays complete")
- **Evidence:** `ProcessDependents` has only `list`/`remove` for a whole process (`dependents.ts:10-13`). They are used only in `DELETE /processes/:id` (`processes.router.ts:357,360`). `PATCH /processes/:id` (`:281-300`) builds the affected list from M5 rows only.
- **Expected:** A change of main category or removal of a route lists and handles M8 precursor links, M6 source-stream allocations, etc. that depend on the category or route. Relevant precursors are per route (M4-R7).
- **Actual:** The seam cannot express it. Once M6–M8 exist, a category change will silently leave their records attached to a process whose category and routes no longer match.
- **Fix:** Extend the interface, for example `listOnSetupChange(tx, processId, { newCategory, droppedRoutes })` with its matching `removeOnSetupChange`, and call it in PATCH before `requireConfirmation`. Add this to the M6/M8 checklists.
- **Retest:** A test registering a fake dependent: a PATCH that changes the category must return 409 listing its records.

### F7 — Activity level in the process list does not open a calculation trace (Low)
- **Ref:** Design system §13 ("Every calculated value opens a calculation trace"); CLAUDE.md UI rules
- **Evidence:** `apps/web/src/features/processes/ProcessListPage.tsx:186` renders `formatExact(p.activityLevel)` as plain text. The detail page does wrap it in `TraceButton` (`ProcessPage.tsx:290`).
- **Fix:** Wrap it in `TraceButton` with the same AL trace, or link it to the detail balance.
- **Retest:** The web test clicks the activity level in the list and expects the trace drawer.

### F8 — Duplicate route IDs in `PUT /production` are silently accepted (Low)
- **Ref:** G8
- **Evidence:** `ProductionRequest.routes` (`processes.ts:101`) has no uniqueness refine, unlike `internalUses` (:106). In probe P9, sending the same `routeId` with 10 t and 20 t returned 200 with an activity level of 20.
- **Fix:** Add `.refine(unique routeId, 'Enter each route once.')`.
- **Retest:** The same request returns 400.

### F9 — Audit action labels do not match D22 (Low)
- **Ref:** G3, D22 ("each with its own audit entry under the action 'Change goods category', 'Remove route', …"); design system §13 ("audit entries use the same verb")
- **Evidence:** `processes.router.ts:258-259` picks the action from `input.goodsCategoryCode !== undefined`. Probe P4: deleting a route with production (confirmed) is audited as `"Save process"`. A rename that also sends the *unchanged* category is audited as `"Change goods category"`.
- **Fix:** Decide the action after loading the row: `changed` gives "Change goods category"; dropped routes with data give "Remove route"; otherwise "Save process".
- **Retest:** Repeat probe P4 and expect `Remove route` and `Save process` respectively.

### F10 — A route-relevant included category can be saved with no routes (Low)
- **Ref:** M5-R1, D16 ("each with the routes it is made by"); template `A_InstData` (a)
- **Evidence:** `checkSetup` only validates the listed routes (`processes.router.ts:89-93`); `IncludedCategoryInput.routeCodes` defaults to `[]`. Probe P6: `aluminium_products` including `unwrought_aluminium` with `routeCodes: []` → 201.
- **Fix:** Require at least one route when the included category is `routeRelevant`, in the API and the DB guard. Alternatively, record in the spec that this is allowed.
- **Retest:** Probe P6 → 400 on `includedCategories[0].routeCodes`.

### F11 — The UI drops `defaultRef` when a stored default value is edited (Low)
- **Ref:** G7
- **Evidence:** `QuantityInput.tsx:17-22`: `draftFrom` and the draft→input conversion carry value, unit, provenance and source but not `defaultRef`. The shared schema requires `defaultRef` when provenance is `default` (`quantity.ts:25-28`). Any save of a form containing a default-provenance amount (copied in a new version, or entered by API) fails validation until the user changes provenance.
- **Fix:** Keep `defaultRef` in `QuantityDraft` and send it back.
- **Retest:** A web test with a `provenance: 'default'` amount, saved unchanged → the request body contains `defaultRef`.

### F12 — `*_default_ref` is an unchecked UUID (Low)
- **Ref:** G7 ("a default value names the library entry it came from")
- **Evidence:** The columns `*_default_ref uuid` have no FK (migration :214, :285, :323 …). Probe P11: `provenance: 'default', defaultRef: <random uuid>` → 200.
- **Fix:** FK to `library_factor(id)` (or the table that defaults will live in) within the pinned library version, or validate it in the API. This can be deferred until M6 introduces defaults, but it should be decided now.
- **Retest:** A random `defaultRef` → 400.

### F13 — Clone silently drops included-category routes missing from the new library (Low)
- **Ref:** D23 ("rows whose codes are not in the new period's library are skipped and listed in the clone result's `skipped` notes")
- **Evidence:** `copiers.ts:92` filters `route_codes` without pushing a note. Main-category routes (:71) and categories (:83) do add notes. Also, D23 names the field `skipped`, but the API returns `notes` (`periods.router.ts:331-336`).
- **Fix:** Push a note when the filtered array is shorter. Align the field name with D23, or update D23.
- **Retest:** A unit test of `copyProcessSetup` with a library lacking one included route → a note is present.

### F14 — Stale confirmation: `confirm=true` deletes whatever exists at that moment (Low)
- **Ref:** Beyond spec (M5-R5/R6, D22)
- **Evidence:** `requireConfirmation` (`dependents.ts:19-27`) ignores the list once `confirm` is true. A contributor can add data between the 409 and the confirmed request, and that data is deleted without having been shown. Traced, not executed.
- **Fix:** Return a fingerprint of the affected list with the 409 and require it back with `confirm` (as M4 publish does with `diffFingerprint`). Answer 409 again if it changed.
- **Retest:** 409 → add data → confirm with the old fingerprint → 409 with the new list.

### F15 — Every single-process request reloads the whole version several times (Info)
- **Ref:** Beyond spec (performance)
- **Evidence:** `loadProcessDetail` → `loadVersionProcesses` loads all 6 tables and the library for the version and filters afterwards (`load.ts:109-121`, `:228-231`). PATCH runs it 3 times (`processes.router.ts:262-263, 279`, then `:328`). Completed-by names are looked up one query per user (`load.ts:130-140`). Bounded by 10 processes, so this is not an N+1 risk today.
- **Fix:** Filter by `process_id` when `only` is set; batch the user lookup with `where id in (…)`.

### F16 — "Complete only with no critical check" is enforced only in the API (Info)
- **Ref:** D20, G2
- **Evidence:** `guard_production_process` (migration :445-450) checks the role but not the checks. Probe P7: a consultant's direct `UPDATE production_process SET status='complete'` on an unbalanced process succeeds. D20 places the rule in the API until M11, so this is recorded for M11: the approval guard (M3-R7) must recompute the checks and must not trust `status`.

### F17 — D18 back-fill changed published library rows with no audit entry (Info)
- **Ref:** G3, M4-R2
- **Evidence:** Migration :27-43 disables user triggers (freeze guard and audit) to update 2026.1. The change is owner-approved (D18), but the audit trail of the published version does not show it.
- **Fix:** Insert one explanatory `audit.audit_log` row in the migration (system actor), or record it in the M4 review notes.

### F18 — Spec gaps (Info)
- **Ref:** Spec gap
- (a) M5-R3 says "Σ quantity per CN + internal consumption reconciles with activity level". D17 redefines the balance to include non-CBAM consumption and internal use per consumer. The bundled module file should be updated to match D17/D19.
- (b) No rule covers AL = 0. The engine will raise a blocking issue (calculation-reference rule 3), but M5 lets such a process be marked complete. Consider an M5 critical check.
- (c) No rule for Σ sold > produced beyond a warning (M5-C07). The spec says this feeds the importer summary; confirm with the owner that a warning is enough.
- (d) The bundled spec has no plausible range for qualifying parameters (see F4). Add one to M4 (M4-R8 range bands) so M11 can use it.
