# Phase 2 plan — Calculation core (M5 to M10)

- **Started:** 2026-09-30
- **Gate (spec §10):** the engine matches the official EU template results on its examples and one real client dataset.
- **Order:** M5 → M6 → M7 → M8 → M9 → M10, one branch each (`m05-processes`, …). Aluminium is the first sector the engine is proven on (spec §10); M5 itself is configuration-driven and works for every goods category in the library.
- **Base:** `m05-processes` is stacked on `m13-evidence` (which contains M3 and M4). PRs #5, #7 and #8 must merge first.

## Decisions

Numbering continues from phase 1 (D1–D15). Spec sections 3 and 4.3 are updated to match.

| # | Decision |
|---|---|
| D16 | **Process model follows the template (asked 2026-09-30).** A production process (template `A_InstData` (b), `D_Processes`) has a name, a **main goods category**, and up to five **included categories** — relevant precursors produced inside the same system boundary (the template's "bubble approach"), each with the routes it is made by (`A_InstData` (a)). Production of the main category is entered **per route** (`D_Processes` (a)); the sum is the activity level, the SEE denominator. A category that is not route-relevant has one row with no route. An included category must be a relevant precursor of the main category, directly or through other precursors, as configured in M4 (G9). At most 10 processes per period version (P1–P10) and at most 10 distinct categories across them (G1–G10), because the template has no more rows. |
| D17 | **Goods and the production balance.** A process makes one or more goods: a CN code of its **main** category (M5-R2, enforced by a foreign key to the pinned library's CN list) with an optional product name (`Summary_Products` H). Each good has the quantity produced, and the quantities sold to the EU and to other markets (spec 4.3, for the importer summary). The process also has the quantity consumed by each other process of the installation (`D_Processes` (c)) and the quantity consumed for non-CBAM goods ((d)). "Produced for the market" ((b)) is **not entered**: it is the sum of the goods' quantities, so the two cannot disagree. The balance is the template's control row (e): activity level − Σ goods − Σ consumed by other processes − non-CBAM. Quantities use the unit of the main category (t, or MWh for electricity). |
| D18 | **Qualifying parameters are configured in M4 (asked 2026-09-30).** `qualifying_parameter_def` gains `required`, `value_kind` (`number`, `text`, `choice`), `dimension` (for numbers: `fraction` for % values, `mass_ratio` for t scrap per t) and `choices`. The published version 2026.1 is **back-filled by the migration** (the only change ever made to a published version, and only to add these attributes): every parameter is required except those the template marks "if known" or conditional (reducing agent, steel mill identification number, concentration if hydrous solution); "Calcined or not" and the reducing agent are choices (the reducing-agent list is the template's `CONST_ReducingAgent`). Values are stored per good, keyed by the parameter's position; numeric values carry the full quantity column group (G5). The platform admin edits the definitions per draft library version. |
| D19 | **Balance tolerance is a library setting (asked 2026-09-30).** New table `library_setting` (versioned, frozen on publish, cloned into drafts, shown in the diff). Key `production_balance_tolerance`, a fraction of the activity level; 2026.1 is seeded with 0.005 (0.5 %). The periods pinned to a version use its tolerance (G8). |
| D20 | **Checks now, issues in M11.** M5 computes its checks with a pure function in `packages/shared` (`processChecks`), each with a rule ID (M11-R6), a severity and the record it concerns. The API returns them with every process; `processIssues(tx, periodVersionId)` is the provider M11 will persist as issues. Until M11 exists, a process can be **marked complete** only with no critical check open; the balance outside tolerance (M5-R3), a missing required qualifying parameter (M5-R4), a missing production amount and a process without goods are critical. Any change to a process or its data returns it to draft. Only admins and consultants mark complete. |
| D21 | **Who changes what.** Admins and consultants configure: create, rename and delete processes, choose categories and routes, add and remove goods, mark complete. Contributors of the installation enter data: production per route, goods quantities, qualifying parameter values, internal and non-CBAM consumption. Reviewers read. Recipients see no process data (like evidence, D15). The database repeats the split: row policies for insert and delete, and a trigger that refuses a contributor's change to set-up columns. |
| D22 | **Confirmations (M5-R5, R6).** Changing the main category, removing a route that has a production amount, deleting a good that has data, or deleting a process with any data answers **409 `confirm_required`** with the affected records listed; the client repeats the request with `confirm: true`. Only then are the affected rows deleted, each with its own audit entry under the action "Change goods category", "Remove route", "Delete good" or "Delete process". Later modules (M6–M9) add their own dependent records through `processDependents` so the list stays complete. |
| D23 | **Pins, clone and new versions.** M5 rows carry the period version's pinned library version, with foreign keys to the library tables; if a draft's pin changes, the change cascades to the process rows and the foreign keys check that every category, route, CN code and parameter still exists. **Clone** (M3-R6) copies processes, included categories, routes and goods (CN code, product name) with no quantities or parameter values; rows whose codes are not in the new period's library are skipped and listed in the clone result's `skipped` notes. **New version** (M3-R5) copies everything, including quantities, parameter values and the evidence links of processes and goods. |

## Tables (M5)

All carry `tenant_id`, `client_id`, `installation_id`, `period_version_id` and `library_version_id`, call `app.register_business_table()` and `app.register_period_table()`, and use the quantity column group (`<x>_value, _unit, _si, _source, _provenance, _default_ref`).

- `production_process` — name, position (1–10), main category, non-CBAM consumption, status (`draft`/`complete`).
- `process_included_category` — additional category and its routes (`route_codes`).
- `process_route` — route of the main category and its production amount.
- `process_good` — CN code, product name, produced / sold to EU / sold elsewhere.
- `process_good_parameter` — qualifying parameter value (number with its quantity group, or text).
- `process_internal_use` — amount of this process's output consumed by another process.
- M4 additions: `library_setting`; new columns on `qualifying_parameter_def`.
